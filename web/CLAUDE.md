# Frontend (`web/`)

Vite + React 19 + TypeScript SPA: the shell + auth plus the full feature surface (catalog CRUD, import/export and repo sync, the Hierarchy and Graph views, the Errors report, lenses, the namespace/label/annotation/tag/type/lifecycle registries, user/feature management, MFA, password reset, and the changelog). Routes are lazy. New capability that Lettuce already has? Port Lettuce's building blocks (see "Not yet ported" at the bottom) rather than inventing new ones.

- Dev server: `cd web && npm run dev` (port **5174** — not Vite's 5173 default, so Toadie can run beside Lettuce). All backend routes live under the `/api/` namespace and Vite proxies the single `/api` subtree → `http://localhost:8081`. Any other path is served as `index.html` so React Router owns the SPA URL space and browser reloads don't collide with API routes.
- Production build: `cd web && npm run build` → static files in `web/dist`. In the Docker image these are baked in and served by the Ktor server itself (via `WEB_STATIC_DIR`; see `plugins/Routing.kt`), so production is single-origin and there is no Vite proxy — the SPA and `/api` share `http://localhost:8081`.
- Regenerate API types: `cd web && npm run gen:api`. Reads `server/src/main/resources/openapi/documentation.yaml` directly (no server needed) and writes `web/src/api/schema.ts`. Run this after editing the OpenAPI spec; commit the regenerated `schema.ts` in the same change.
- **Quality gates (the frontend counterpart of the backend's detekt)**: `npm run lint` carries `eslint-plugin-sonarjs` (recommended) plus core size/complexity backstops — zero-findings gate; rule tuning lives in `eslint.config.js` ONLY, one commented override per deliberate idiom, and any inline `eslint-disable` needs a justifying comment. `npm run knip` is the dead-code gate (unused files/exports/dependencies; `knip.json` ignores the generated `schema.ts`) — keep exports that only the declaring file uses un-exported, and delete what knip flags rather than ignoring it.
- **Build version stamp**: `vite.config.ts` injects `__APP_COMMIT__` (short sha, `+dirty` when the worktree has uncommitted changes) and `__APP_COMMIT_TIME__` (commit ISO timestamp) via `define`, declared in `src/vite-env.d.ts`. Env vars `GIT_SHA`/`GIT_COMMIT_TIME` override the local-git lookup — the Dockerfile's SPA stage sets them explicitly (its worktree never matches the index, so the dirty check would false-positive), and CI can do the same when building without `.git`. `src/components/VersionStamp.tsx` renders `v<APP_VERSION> · <sha> · <time>` at the bottom of the navbar (`App.tsx`) and under the login card (`components/AuthCard.tsx`).

## Layout conventions

- **Flat directories**: `pages/`, `components/`, `hooks/`, `utils/`, `api/`, `changelog/`, `locales/{en,pl}/`, `test/` — no deeper nesting, no per-feature folders (a feature contributes files into these).
- **Default exports for components/pages**, named exports for everything else; **no path aliases** — relative imports only.
- **Co-located tests**: `Foo.test.tsx` sits beside `Foo.tsx`; shared test scaffolding lives in `src/test/` (`setup.ts` forces `en`, `render.tsx` is the provider wrapper — it and every file-local `MantineProvider` must pass `env="test"`, or Select/Popover interaction silently fails under happy-dom; `http.ts` holds the fetch stubs).
- **CSS modules only where the theme can't express it**: styling belongs in `src/theme.ts` (Mantine `createTheme` — component `extend`s, defaultProps) with `src/theme.module.css` for the class-level parts; a per-component `*.module.css` is the exception, not the pattern.
- Pages are **lazy** (`React.lazy` in `App.tsx`); new routes register above the `path="*"` NotFound catch-all (LAST child, never feature-gated), and nav entries append to `NAV_ITEMS` (the `label` is a typed i18n key; `adminOnly?` gates admin leaves — the Lettuce feature/role-filter machinery slots back in here as features arrive). `NAV_ITEMS` is a mixed `NavLeaf | NavGroup` list: a group (Dictionaries, Metadata) renders as a `component="button"` parent `NavLink` with `defaultOpened` children — groups start OPEN so child links stay in the DOM (tests and e2e click them directly), only leaf clicks close the mobile drawer, and the active-link matcher runs over the FLATTENED leaves.

## The typed API layer (`src/api/`)

The OpenAPI spec at `server/src/main/resources/openapi/documentation.yaml` is the contract between backend and frontend — hand-maintained, not auto-generated from routes. Swagger UI is at `http://localhost:8081/openapi` (dev). The layer is small hand-written modules:

- **`http.ts`** (transport): `authedFetch()` with the **single-flighted silent refresh** — on a 401 it exchanges the stored refresh token once (concurrent 401s share one in-flight `/refresh` call) and retries once; a DEFINITIVE rejection (no refresh token, or 401/403 from the server) clears the session and signs out, while a TRANSIENT failure (network/timeout/5xx/429/malformed body) keeps the session so a later retry can succeed — **never collapse the two** (a network blip must not erase a valid session). `ApiError` (status + parsed body; read RFC 7807 fields via the `detail`/`instance` getters, never hand-cast `err.body`), and the two standard wrapper shapes **`jsonRequest<T>()`/`voidRequest()`** every ordinary endpoint wrapper uses, plus **`buildQuery()`** — the query-string builder behind the list/graph/export wrappers (skips null/undefined/""; `false` and `0` ARE sent, so an omit-when-false param is passed as `value || undefined` at the call site). Reach for the raw `authedFetch`/`safeJson` primitives only when a wrapper genuinely inspects the Response. Every transport fetch carries `timeoutSignal()` (30 s, feature-detected for happy-dom) — a hung request rejects with a `TimeoutError` DOMException instead of pending forever; new `fetch` call sites in `api/` must attach it.
- **`session.ts`**: token/roles/userId storage under the `toadie.auth.*` localStorage keys, written by `persistSession(LoginResponse)` on login/refresh, and the render-time accessors (`isAdmin()`, `getUserId()`, …) — plain reads, no reactive store.
- **`auth.ts`**: login + the MFA exchange, self-service password reset, and logout (`logout()` is best-effort — the revoke POST may fail, `clearSession()` always runs, the function never throws).
- The types come from the generated `schema.ts`; a new endpoint's wrapper goes into its feature's module (a new feature area gets a new module — never a catch-all file). Avoid heavyweight client generators (Orval/Kiota) — the lightweight pairing of `openapi-typescript` (types only) + hand-written fetch is intentional.

`openapi-typescript` is installed with `--legacy-peer-deps` because its declared peer is TS `^5` while the scaffold uses TS 6; the generated output is compatible. If you re-`npm install` from scratch, use `npm install --legacy-peer-deps`.

## Error handling

- **ErrorBoundary** (`components/ErrorBoundary.tsx`): a page render crash must never white-screen the app. `RouteErrorBoundary` wraps the `<Outlet />` inside `AppShell.Main` (header/nav survive; keyed by `location.pathname`, so navigating anywhere recovers), and a plain `ErrorBoundary` in `main.tsx` is the last resort for shell crashes. Don't add per-page boundaries — the two mounts are the model.
- **Catch-all 404**: `pages/NotFound.tsx` is the LAST `path="*"` child of the Shell route. New routes go above it.
- **Chunk-load recovery**: `main.tsx` listens for `vite:preloadError` (a redeploy 404s the old hashed chunks) and reloads once, rate-limited via sessionStorage (`toadie.chunkReloadedAt`, max one reload/minute) so a genuinely missing chunk falls through to the ErrorBoundary instead of looping.
- **Query retry policy**: the `QueryClient` in `main.tsx` uses `shouldRetryQuery` (`api/http.ts`) — NEVER retry a 4xx (the answer won't change; retrying only delays the error UI), at most two retries for transient failures.
- **Messages**: never render `error.message` (it's the internal `API <status>` / the browser's "Failed to fetch") — map statuses to i18n keys via the shared mappers in `utils/saveError.ts`: `saveErrorMessage(err, t, keys)` for mutations (per-status keys + a `failed` fallback) and `loadErrorMessage(err, t)` for list loads. Errors render inline as `color="red" variant="light"` Alerts — never as toasts.
- The `@mantine/notifications` host is mounted in `main.tsx` (top-center, autoClose 2500, limit 3 — deliberately not in App, so unit tests never mount it). **Success toasts only, with fixed vocabulary only** (`showSuccessToast(t("<area>.toast.*"))` in `utils/toast.tsx` — teal, never user-entered values; errors stay inline).

## Shared list-page building blocks (the CatalogFiles.tsx template)

Every list page composes the same ported Lettuce blocks — copy `pages/CatalogFiles.tsx`, don't re-derive:

- **State**: filters in `useStoredState` (persisted under `toadie.viewSettings.<viewKey>.filter.*`, text filters debounced 300 ms — the DEBOUNCED value goes into the query key, and actions like the list's Export read the DEBOUNCED value too, so a click never operates on a slice the table isn't showing), sort/page/pageSize from `usePagedSort(initialSort, filterDeps, { key, sortFields })` with `SORT_FIELDS ... as const`. Every catalog-derived query (the list, the identities pool, the Errors report, the graph, the editor's live check) keys under the `["catalogFiles", …]` prefix, so one `invalidateQueries(["catalogFiles"])` after any catalog mutation refreshes them all.
- **Query**: `useQuery({ queryKey: ["<area>", page, pageSize, sortParam, ...filters], queryFn: list<Area>(...), placeholderData: keepPreviousData })`.
- **Chrome**: `FilterPanel` (collapsed by default, persisted, active-count badge) + `ClearableTextInput` for freetext filters (debounced) and dictionary-backed Selects for closed value spaces (`NamespaceFilterSelect` over the namespaces dictionary; grouped/searchable Selects over the registries — all undebounced: Select changes are discrete); `SortHeader` in the `Table.Th`s; `TableLoadingRow` (`isLoading && !data`) / rows / `EmptyState` (`!isError`) triage in the tbody; a `color="red" variant="light"` Alert with `loadErrorMessage` ABOVE the table on error; `PaginationBar` below. **The catalog-file filter set is a shared surface**: `hooks/useCatalogFileFilterState.ts` (nine per-view-persisted slots, normalized `values` for query keys/params, `deps` for `usePagedSort`, the label→labelValue reset) + `components/CatalogFileFilterControls.tsx` (the controls with their option sources and the stale-persisted-value appends; the Type Select groups options by kind with kind-PREFIXED option values, since the same type may be allowed for several kinds and Mantine needs unique values) — rendered inside `FilterPanel` by the Files list, Hierarchy, AND the Graph page, matching the server's identical list/graph filter params. **The Kind pills live OUTSIDE the panel** (`components/CatalogKindPills.tsx`, always visible directly above the content on all three pages) and are a VISIBLE-kinds set, not a filter: all kinds start ON (`visibleKinds` slot, per-view persisted, junk falls back to all-on), all-on sends NO `kind` param, a subset rides the server's any-of `kind` IN param, and NONE on means show nothing — the hook's `noKinds` flag disables the page's query and the page renders empty itself (the API cannot express match-nothing; `keepPreviousData` would otherwise keep stale rows). The pills never count into the FilterPanel's active-filter badge. A new catalog filter extends the hook + controls (and both endpoints), never one page. **Kind tiers are a purely VISUAL marker**: `KIND_TIERS`/`kindTier` beside `ENTITY_KINDS` (`utils/catalogFileForm.ts` — the fill-in priority: 1 Domain/System/Group, 2 Component, 3 Resource/API, 4 User; the lookup folds case because the graph endpoint spells kinds lowercase) rendered by `components/KindTierDot.tsx` — an `aria-hidden` circled numeral with a native-`title` tooltip (`catalog.tier.tooltip`), styled by `theme.module.css` `[data-tier]` variants — before the kind name on every kind surface (pills, the Files/Hierarchy/Graph/Errors/import kind badges via `leftSection`, the registry pages' applies-to badges, and the kind Selects/MultiSelects via the shared `renderKindOption`); `aria-hidden` is load-bearing, and so is the numeral being CSS `::before` content rather than a DOM text node: tests and e2e locate pills/badges by the bare kind name (getByText exact included), so the dot must contribute NO text. Nothing behavioral hangs off tiers. **Lenses ride this surface**: `components/LensPicker.tsx` (one shared component, rendered through `FilterPanel`'s `aside` slot — the header row beside the toggle, reachable with the panel collapsed) on the Hierarchy, Files, Graph, AND Errors views — a Select over `hooks/useLenses.ts` (query key `["lenses"]`, invalidated after every lens mutation) grouped Private/Public (foreign public lenses labeled `name — creator`), whose pick bulk-applies the lens payload via the hook's `applyValues` (the one bulk setter — absent kind = all pills on); the selection is sticky `useState`, deliberately unpersisted, with a "Modified" badge when the current filters diverge (`utils/lensFilters.ts` — the canonicalized values⇄payload mapping + equality); the actions Menu holds Save-as (modal: name + visibility radios), and — creator-only — Save changes (overwrites the payload with the CURRENT filters), Rename/visibility (keeps the STORED payload), and Delete.
- **Whole-file operations** live in one place, `components/CatalogFileOperations.tsx` (the Files list AND the Hierarchy tree), and are mirrored as buttons on the EDITOR: **Export as YAML** (one file, via `useCatalogDownloads`), **Overwrite with YAML**, and **Sync from source**. The Sync item is ALWAYS rendered and merely `disabled` without a source reference — vanishing read as "this file can never be synced" rather than "set a source first" — which is why the prop is `sync?: {onSync, enabled}`: a caller either knows the file's source state or passes nothing at all (the Hierarchy passes nothing, since graph nodes carry no `sourceUrl`). **`components/OverwriteWithYamlModal.tsx`** is the Sync modal with the repo fetch swapped for a pasted/picked YAML: same `parseCatalogYaml` + `pickRepoDocument` + `YamlDiffView` + confirm shape, but it writes through the ordinary **PUT, never `syncCatalogFile`** (the sync endpoint stamps `lastSyncedAt` and the baseline, which would claim the file is in sync with a repo it never touched) and it **passes the stored `sourceUrl` back** (PUT is a full replace — omitting it silently unlinks the file from its repo). `components/SyncStateText.tsx` renders the No-source/Never-synced/relative-time + Local-changes strip for the list column and the editor alike. **Whole-workspace export is API-only** (`GET /api/v1/files/export`): the bottom-bar button was removed for saying "Export YAML" without saying what it exported.
- **The editor RE-SEEDS after a whole-file operation** (v1.13.1). Mantine's `form.initialize` is a one-shot latched on a ref, and the edit page's guarded-initialize line only ever fires once — so Overwrite/Sync replacing the stored document left the fields AND their dirty baseline showing the old one, which meant a later Save wrote the old document back over what just landed. Both modals therefore take an optional `onCompleted` fired only on a SUCCESSFUL write (`onClose` cannot tell a Cancel from a completion), and the edit page re-seeds with `setInitialValues` → `setValues` → `resetDirty` (the Namespaces re-seed-after-save idiom; there is no supported way to re-run `initialize`). Two rules: the re-read goes THROUGH `queryClient.fetchQuery` on the page's own detail key, so a failure lands in that query's error state and the editor degrades to its load-error branch instead of leaving a live Save over a stale form; and it is **callback-driven, never an effect on `data`** — the detail query also refetches in the background (window focus), and re-seeding on any data change would discard whatever the user is typing.
- **Two kinds of field problem, two colours (v1.14.0).** Hard client validation BLOCKS the save and stays Mantine's red; a live-check FINDING does not block it (it routes through Save-anyway), so it shows ORANGE — the same orange as the Save-anyway button, `CREATED_WITH_FINDINGS` rows and the local-changes badge. Painting a finding red would make a legitimately saveable file (an imported-with-findings one) look broken. A hard error always wins on a field that has both. `utils/fieldFindings.ts` routes the wire finding to its control: `spec.X` → the form path `X` (the form's value names mirror the spec names exactly), `metadata.tags` → `tags`, and — the awkward one — labels arrive as the bare `metadata.labels` for every row, identified only by `reference`, which is `key` when the KEY is rejected and `key=value` when the value is off its closed list, so **split on the first `=`** (a label key cannot contain one). Annotations always name a key; a multi-valued ref field emits one finding PER bad entry, and those name the entry in the message (single-valued fields don't — the input already shows the value). `utils/findingProps.tsx` returns the props to spread **after** `getInputProps` (later props win, and `getInputProps` returns a plain object). Findings are **presentational only, never `form.setFieldError`**: Mantine replaces the whole error map on every submit and clears a field's error as you type, so a form-state finding would flicker away — and form state must stay the sole province of the rules that actually block saving. The check runs ONCE in `CatalogFileEditor` (`hooks/useDocumentCheck.ts`) and feeds both the panel and the fields. Both editor pages set `validateInputOnBlur: true`; the registry Selects therefore spread `getInputProps` FIRST and override `value`/`onChange` after, or they would receive no `onBlur` and silently skip blur validation.
- **The same two colours per PILL (v1.14.1).** On the multi-value controls — the relation `TagsInput`s and the tags `MultiSelect`, the only pill-bearing fields that can carry findings — the box tint cannot say WHICH of six entries is at fault, so the offending pill is tinted too (`.findingPill`/`.invalidPill` in `theme.module.css`). Mechanism: Mantine's **`renderPill`** prop (`components/FindingPill.tsx`, a render-callback factory beside its component like `renderKindOption`) — not a `Combobox`+`PillsInput` rewrite and not `nth-child` guessing. It re-renders the pill wholesale, which is safe because neither component styles its pills (both pass `classes: {}` to `useStyles`) and `Pill` takes size/variant from the surrounding contexts, so an unmarked pill is byte-identical to before; `Pill`'s remove button is `color: inherit`, so tinting the text carries the `×`. Matching a finding to a pill is an **exact string compare** against `reference` — the server echoes the stored value verbatim (`checkDocument`/`tagFindings`), so nothing needs normalizing, and an entry edited since the debounced check answered simply stops matching until the next one lands. The verdict itself is the pure `pillVerdict` in `utils/fieldFindings.ts`, and it applies `findingProps`' precedence at entry granularity — **the pills follow the field, one class of problem at a time**: while the field carries a hard error only grammar-invalid entries are marked (red), otherwise only flagged ones (orange). Red is gated on the field's `hardError` rather than on the predicate alone so a half-typed reference does not flash red under `validateInputOnBlur`; once validation HAS run, every offending entry lights up, not just the first one the rule's message names. Each call site passes its own entry predicate-with-reason — `isValidEntityRef` / `isValidTag`, both exported from `utils/catalogFileForm.ts` and shared with the form rules so the grammar has one definition. The entry-naming field messages **stay**: the pill says which, the message says why, and colour is never the only carrier.
- **Delete**: `useDeleteConfirm` + `ConfirmDeleteModal` — the hook owns modal state and the success toast, the page owns `invalidateQueries`.
- Row action buttons carry interpolated aria-labels (`<area>.editAria` etc.) — unit tests and e2e locate by them; table tests query cells by **text**, not `cell` role names. The catalog-files list bundles its row actions under one **Operations** `Menu` instead (trigger aria-label `catalog.operationsAria` with the name interpolated; items are plain `menuitem`s — only one row's menu is open at a time; e2e drives it via the `rowOperation` helper).

## Forms (the CreateCatalogFile/EditCatalogFile template)

- Shared vocabulary in `utils/<area>Form.ts`: the `<Area>FormValues` type, length constants mirroring the server's, a `<area>FormValidation(t)` factory (rules identical to the server's — keep them in sync), and `toRequest`/`fromResponse` mappers. The catalog form is **kind-aware**: `KIND_FIELDS`/`KIND_REQUIRED` mirror the server's per-kind tables, every rule no-ops for non-applicable fields (a kind switch leaves no stale errors), and `toCatalogFileRequest` strips fields foreign to the submitted kind while keeping Group `children` / User `memberOf` present-and-empty. The field block lives in `components/<Area>FormFields.tsx`; the pages own submit/error/navigation. **Reference pickers**: every ref field is an Autocomplete/TagsInput fed by `hooks/useCatalogIdentities.ts` (the pool loop over the list endpoint, 5-min cache, refreshed by `["catalogFiles", …]` invalidations) through the pure `utils/refSuggestions.ts` (per-field target kinds; every suggestion is the FULL identity `kind:namespace/name` — unambiguous regardless of default kind or current namespace). Free text stays legal in the WIDGET (typed short forms still resolve), and the pickers EXCLUDE the current identity from their options (an entity may not reference itself). **Resolution is a SOFT concern — the client no longer blocks on it**: `catalogFileFormValidation(t)` validates grammar and per-kind rules only, the pages attempt a STRICT save, and on a 400 they ask `softRejectionFindings` (`api/catalogFiles.ts` — `ApiError` 400 → `POST …/check`) whether the rejection was soft; findings open the shared `SaveAnywayModal` (Cancel / **Save anyway**, which retries the same request with `{ allowInvalid: true }` → the `?allowInvalid=true` query param), while a finding-less 400 falls through to the ordinary inline `catalog.validationError` Alert. This one flow covers unresolved/wrong-kind/kind-less/self references AND registry findings the client cannot see (legacy or imported-with-findings values) — which is what keeps imported-invalid files editable. The editor's live `ReferenceCheckPanel` shows the same `/check` findings (references + registry checks) as the advisory surface; its findings mean "a strict save will ask for confirmation". **The namespace field is a Select** over the namespaces dictionary (`hooks/useNamespaceOptions.ts`, sharing the `["dictionary", "namespaces"]` key with the `/namespaces` page; also surfaces `defaultNamespace`, the entry flagged DEFAULT; a stored value no longer in the dictionary is appended so it keeps displaying) — catalog writes accept ONLY defined namespaces (server-enforced, strict). Blank means the FLAGGED default: the submit path sends it blank (the server resolves authoritatively) while the editor's preview/check mapping passes `defaultNamespace` into `toCatalogFileRequest(values, defaultNamespace)` so the YAML preview shows the concrete namespace that will be stored; a failed options load shows its own hint while leaving the field enabled, and an empty dictionary the `noNamespacesDefined` hint — the sibling pickers' presentation (the server is the actual gate). **The labels section is registry-constrained pickers**, not free key/value inputs: each row is two Selects fed by `hooks/useLabels.ts` (the `["labels"]` key, shared with the `/labels` page) — the key Select offers only ADMIN-registered labels allowed for the document's kind (minus keys other rows hold), the value Select that label's closed list; picking a key resets the row's value, a stored-but-no-longer-offered key/value is appended to its own row's options so it keeps displaying (the server's strict 400 then names the problem), zero labels for the kind disables Add behind a hint, and a failed registry load keeps existing rows rendered. **The annotations section gates its KEYS through the registry** (`AnnotationsFieldset`): each row's key is a Select fed by `hooks/useAnnotationKeys.ts` (the `["annotationKeys"]` key, shared with the `/annotations` page) offering only ADMIN-registered keys allowed for the document's kind (minus keys other rows hold; a stored-but-no-longer-offered key is appended to its own row's options), while the VALUE stays a free `TextInput` (values are not registry-checked); zero keys for the kind disables Add behind a hint, and a failed registry load keeps existing rows rendered. **The tags field is a grouped `MultiSelect`** (`TagsMultiSelect`, fed by `hooks/useTagCategories.ts` — the `["tagCategories"]` key, shared with the `/tags` page): options are the tags of ADMIN-defined categories whose kinds include the document's kind, grouped under each category's name; stored tags no longer offered are appended under the `catalog.staleTagsGroup` group so files keep rendering, zero categories for the kind shows the `noTagsForKind` hint, and a failed registry load the `tagOptionsFailed` hint — the field stays rendered either way. **The Type field is a registry Select** (`TypeSelect` in `CatalogFileFormFields.tsx`, fed by `hooks/useEntityTypes.ts` — the `["entityTypes"]` key, shared with the `/types` page): options are the document's kind's ADMIN-defined type dictionary (V15 seeds the well-known Backstage values), a stored value no longer offered is appended so it keeps displaying, a kind with no dictionary shows the `noTypesForKind` hint, and a failed load the `typeOptionsFailed` hint; the field is clearable exactly when the kind's type is optional (System/Domain). **The Lifecycle field is a registry Select too** (`LifecycleSelect`, fed by `hooks/useLifecycleOptions.ts` — the `["dictionary", "lifecycles"]` key, shared with the `/lifecycles` page): options are the GLOBAL lifecycles dictionary (V16 seeds the well-known values), stale stored values appended, never clearable (every kind rendering it requires it); hints `noLifecyclesDefined`/`lifecycleOptionsFailed`.
- Edit prefills via **`form.initialize(...)` guarded by `!form.initialized` during render** — never a `useEffect`. Submit is a plain async fn with local `submitting`/`error` state wrapped by `form.onSubmit`; success → `invalidateQueries` (list + detail) → `showSuccessToast` → `navigate(list, { replace: true })`; failure → `saveErrorMessage` into an inline Alert.
- **Widths**: `Container size="sm"` for simple field forms (the Lettuce rule). The catalog editor is the sanctioned deviation: a document screen rendered as a full-width `Grid` — form (`md=7`) beside a sticky live-preview card (`md=5`, `components/YamlPreviewCard.tsx`). Reuse that split for future document editors.
- `utils/catalogYaml.ts` owns catalog-info.yaml rendering (canonical key order, empties omitted, `default` namespace implicit; `catalogInfoMultiYaml` joins documents with `---` for the export) + the `downloadYaml` Blob helper — client-side by design: even the round-trip kept YAML out of the server (export ships structured documents, import receives them). **`utils/catalogImport.ts` is the generator's STRICT mirror** — `parseCatalogYaml` maps a multi-document YAML back to `CatalogFileRequest`s with per-document error indexes, rejecting unknown keys by name (`apiVersion` is the one accepted-and-ignored key; an ABSENT `metadata.namespace` maps to blank — resolved server-side to the flagged default, so an exported literal-`default` file re-imports identically unless an admin flipped the flag away from `default`) — when the document shape grows a field, extend generator and parser in the same commit (the round-trip property test in `catalogImport.test.ts` catches a one-sided change). The import page (`pages/ImportCatalogFiles.tsx`, `/files/import`) posts only cleanly parsed batches and renders the server's per-row report — the **Check** button runs the same batch through `POST /files/import/check` (the dry-run: identical rows as PREDICTIONS, "Would be created" labels via the `import.checkStatus.*` keys, no invalidation — nothing stored); import always waives the soft checks, so soft-flawed documents STORE as orange `CREATED_WITH_FINDINGS` rows (message = the findings; both created statuses count into the summary), and only structural/namespace failures surface as INVALID rows, not parse errors. Its fetch-from-URL field goes through `normalizeCatalogUrl` (same file — GitHub `/blob/` and GitLab `/-/blob/` browser links rewritten to their raw form) before the server-side `POST /files/fetch` (SSRF-guarded; the guard's uniform 400 maps to the fixed public-https message).

## Source references & repo sync (`components/SyncCatalogFileModal.tsx`)

Each file may carry a `sourceUrl` (its repo copy's https URL) — envelope state beside the document, never in the YAML/round-trip. The editor's `SourceFieldset` edits it (`sourceUrl` in the form values; the pages share ONE strict-save → Save-anyway flow, `hooks/useCatalogFileSave.ts`, sending `{ ...toCatalogFileRequest(values), sourceUrl }` while `/check` keeps receiving the PURE document); the import page tracks `fetchedFrom` (set on a successful URL fetch, cleared by any text change) and passes it to `importCatalogFiles` so fetched batches store referenced-and-synced. The Files list adds the sortable **Last sync** column (`SyncStateCell`: "No source" / "Never synced" / `relativeTimeAgo` (`utils/relativeTime.ts`, `Intl.RelativeTimeFormat` — the ONE relative-time util) + the orange "Local changes" badge via `hasLocalChanges`, `utils/syncComparison.ts`) and passes `onSync` to `CatalogFileOperations` only for sourced rows (the optional prop — Hierarchy never passes it). ## The render graph (`pages/RenderGraph.tsx`)

`@xyflow/react` (React Flow 12) + `@dagrejs/dagre` draw `GET /api/v1/files/graph` (behind the same shared catalog-file `FilterPanel` as the Files list and Hierarchy; the relation-family chips stay separate and unpersisted); both deps ride the lazy `/graph` chunk (the RenderGraph page — the component keeps its name) — keep them out of eagerly-imported modules. The pure shaping lives in `utils/graphLayout.ts` (`filterGraph` relation-family filtering + orphaned-virtual-node pruning, `layoutGraph` dagre-LR → React Flow nodes/edges, `applyManualPositions` the manual-mode overlay) and carries the unit-test coverage; **unit tests stub `@xyflow/react`** (happy-dom can't give it real DOM measurement — see `RenderGraph.test.tsx`'s `vi.mock`; the stub ignores unknown props, so every prop the page relies on must be surfaced in it explicitly), and e2e exercises the real canvas. The custom node (`components/CatalogGraphNode.tsx`) styles by status through Mantine CSS vars only, and the canvas `colorMode` follows `useComputedColorScheme` — never hardcode colors there. Its face is **name + `spec.type`** (the namespace deliberately does NOT ride the node — it says `default` for almost every file; a kind with no type, i.e. User and every virtual node, simply leaves the second line blank, so the fixed `GRAPH_NODE_HEIGHT` box is unchanged). The name owns the WHOLE first line and the kind badge sits on the second beside the type — the badge was previously `position: absolute` over the first line, so long names ran underneath it instead of ellipsizing, and putting it merely *beside* the name is no better: a `2 COMPONENT` badge is over half the 200px box, which leaves room for about eight characters (`checkout-service` became `checko…`). On that second row the type is `flex: 1` **with `minWidth: 0`** — without it a flex item never shrinks below its content width and `truncate` silently no-ops. **Truncation must stay CSS `text-overflow`, never a JS slice** — `render.spec.ts` locates nodes by `getByText(name, { exact: true })` on long generated names, which needs the full string intact in one text node. The name carries the app's ONLY Mantine `Tooltip` (themed in `theme.ts`; every other hover text is a native `title` attribute, which cannot hold badges): name, namespace, title and tag badges, all fed by the graph payload — `GraphNode` gained `type` and `tags` for exactly this, while `description` is deliberately kept OFF the wire (2000 chars per file, and no list-style DTO carries it either). **Namespace frames**: when the visible graph spans TWO OR MORE namespaces, each is drawn inside a labelled region behind its nodes. Two halves, both needed — a bounding box alone would be meaningless, since the layout otherwise scatters a namespace through the ranks. (1) `layoutGraph` builds the dagre graph `{ compound: true }` and `setParent`s every node onto a `ns:<name>` cluster, which is what clumps a namespace together; the cluster needs an explicit `setNode(id, {})` (a `setParent`-created node has an `undefined` label and dagre's `updateInputGraph` skips it), never a per-cluster `rankdir` (that switches dagre onto its far less exercised `recursiveClusterLayout`), and `nodesep` widens to 36 while grouped because the cluster gap comes out at `nodesep + 40` and the frame chrome has to fit in it. (2) `namespaceFrames(nodes)` derives the rectangles from the members' LIVE positions, so Manual-mode drags stretch a frame with no extra machinery — a node's namespace is DATA, so dragging must never be constrained by a box, and overlapping frames are the honest result. The frames render through `components/NamespaceFrames.tsx` into React Flow's **`ViewportPortal`** at `z-index: -1`, deliberately NOT as nodes: they must not be selectable, hit-testable, or counted where nodes are counted (the empty-state check, the `.react-flow__node` e2e locators), and making them React Flow PARENT nodes would be worse still — a parent turns its members' positions parent-RELATIVE, silently reinterpreting every absolute position already stored in the per-user layout document. A single-namespace graph gets no frame and no clustering: the layout is byte-identical to before. **Two layout modes** (a `SegmentedControl`): **Auto** = the dagre layout; **Manual** = `nodesDraggable`, dragged positions overlaid via `applyManualPositions` and persisted **server-side per user** as ONE document (`{mode, positions}` keyed by node id, `GET`/`PUT /users/{id}/graph-layout` — `getGraphLayout`/`setGraphLayout` in `api/users.ts`, query key `["graphLayout", userId]`). **React Flow owns the live node state**: the page holds nodes/edges in `useNodesState`/`useEdgesState`, `onNodesChange` routes every change through `applyNodeChanges` (drags stay fluent), and a sync effect rebuilds the arrays from the dagre `baseLayout` + saved positions ONLY when structure, mode, or the SAVED positions change — **never write `positions` on a mid-drag frame** (that was the v1.7.1 flicker fix: a mid-gesture wholesale node-array replacement resets RF's internal drag state and blanks the canvas). Persist only on a `dragging === false` change, accumulated across the whole batch (a multi-select drag ends several nodes in ONE changes array — last-write-wins would drop all but one), and keep the stable `EMPTY_POSITIONS` constant as the no-layout fallback (a fresh `?? {}` in a dep chain retriggers the sync effect every render). The wire PUT is a **wholesale replace and the client MERGES**: the page holds the full map from the GET and updates only dragged entries — never prune to the currently filtered nodes. Saves are fire-and-forget (drag stops debounced 600 ms; mode switches and **Reset layout** — which clears the positions while staying manual — immediate). A drag must never navigate: the `draggedRef` guard swallows the `onNodeClick` that React Flow fires after a drag gesture. The viewport REFITS when the node SET changes (the `structureKey` effect over the sorted ids — the `fitView` prop fires only at init, so a later filter would otherwise leave the new layout off-canvas at the old pan/zoom) but never on drags, mode switches, or Reset.

## Internationalization (i18n)

The SPA is **N-language by architecture** via react-i18next (`src/i18n.ts`); the shipped bundles are English (THE default and fallback everywhere) and Polish. All user-facing strings go through `const { t } = useTranslation()` / `<Trans>` — **no hardcoded UI text**. Conventions:

- **Resources** live in `src/locales/{en,pl}/<area>.json`, one file per area (`common`, `annotations`, `appShell`, `auth`, `catalog`, `changelog`, `errors`, `hierarchy`, `labels`, `lenses`, `lifecycles`, `namespaces`, `render`, `tags`, `types`, `users` today); `i18n.ts` merges them into a single `translation` namespace, so keys read `area.key` (e.g. `t("auth.signIn")`). Only EN is statically imported — its typed `en` tree is the key canon AND the runtime fallback; every other language is auto-discovered from `locales/<lang>/` via `import.meta.glob`. Bundles are eager on purpose; move non-EN to lazy loading when a 3rd language ships or a bundle grows large.
- **Keys are typed**: `src/i18next.d.ts` augments i18next's `CustomTypeOptions` with `typeof en` from `i18n.ts` (the `@public`-tagged export — knip can't trace the d.ts consumer), so every `t()` call and `i18nKey` is compile-checked against the EN tree — a typo or removed key fails `tsc`/`npm run build`. Fields holding a key are typed `ParseKeys` (from `i18next`), never `string` (the `NAV_ITEMS` `label` pattern); functions taking a translator take `TFunction`, never a hand-written `(key: string) => string`.
- **`common.*` is the shared source**: actions, field labels, shared vocabulary. Reuse it instead of duplicating; build Mantine `Select` option labels from `t()` at render so they translate.
- **Keep key parity vs EN for every shipped language** — a shipped bundle is all-or-nothing: every English key must exist in each `locales/<lang>/` (language-specific plural variants are expected), enforced by `locales/parity.test.ts` (auto-discovers language folders; also pins folders == `SUPPORTED_LANGUAGES`). Use i18next interpolation (`{{name}}`) and plural keys rather than string concatenation.
- **Adding a language** = a complete `locales/<lang>/` folder (every area file, parity-gated) + one code in `SUPPORTED_LANGUAGES` (`i18n.ts`) + one `NATIVE_LANGUAGE_NAMES` line — the Record type and the parity test each fail loudly on a missed step. Server-side, the `LocalizedText(en, pl)` constructor arity is the parity gate for email texts (a new language means a new parameter — every email text becomes a compile error until translated), and `dictionaries/Languages.kt` mirrors `SUPPORTED_LANGUAGES`.
- **Polish voice convention** (inherited from Lettuce): inclusive slash forms, active/direct voice, same tense and meaning as the English; spell out irregular feminines in full. No impersonal/passive dodges.
- The language switcher is `components/LanguageSwitcher.tsx` (header) — a Mantine `Menu` of NATIVE language names (`NATIVE_LANGUAGE_NAMES`, deliberate constants: readable before switching, and `Intl.DisplayNames` yields lowercase forms); choice persists in `localStorage` (`toadie.lang`) and updates `<html lang>` (the `languageChanged` hook in `i18n.ts`). **The user language is ONE synced property since V18**: the switcher also fire-and-forget saves it server-side (`setUserLanguage` — it drives every email sent to the user), and `persistSession` applies the login/refresh response's `language` to the UI — signing in restores the user's language on any device, and an admin change propagates at the ≤15-min silent refresh. Emails render in the RECIPIENT'S stored language (`LocalizedText(en, pl)` in `infra/mail/`, EN fallback).
- **Tests render English**: `src/test/setup.ts` imports `../i18n` and forces `en`, so text-based assertions match the EN resources.

## Theming

**The design language is theme-owned** (Lettuce's "clean enterprise SaaS" posture) — `src/theme.ts` + `src/theme.module.css` are the single source:

- The brand is the 10-stop **`toadie` amber tuple** (warm amber/brown toad scale) with `primaryShade: { light: 7, dark: 8 }` — deep, calm CTAs — and `autoContrast: true`. The brand amber is the interactive accent (buttons/links/active nav inherit it); **never reintroduce `color="blue"` actions**, and when semantic success states arrive, use **teal**, never stock `green` (which would impersonate a brand color).

## Changelog & app versioning

The user-facing changelog is a **build-time artifact** — no DB, no API, changes only with a deploy. `src/changelog/entries.ts` holds `ChangelogEntry` rows (`version`, `date` `YYYY-MM-DD`, `en`/`pl` **markdown** bodies), newest first; the app's only human-readable version is `APP_VERSION` in **`src/changelog/version.ts`** — its own tiny module so the shell's eager imports (VersionStamp, the what's-new dot) never pull the bilingual entries into the main bundle (the entries ride the lazy Changelog chunk only). **A release = the new entry at the top of entries.ts + the bump of that one literal** (the Gradle `1.0.0-SNAPSHOT` is unrelated); `entries.test.ts` pins `CHANGELOG[0].version === APP_VERSION`, so forgetting either half fails the suite. Release convention:

- Write both language bodies by hand (or LLM) — never derive them from commit messages. Bodies are *content*, so they live in the data file, not `locales/`; the PL body follows the Polish voice conventions (inclusive slash forms, active voice).
- Keep dates descending (same-day releases are fine — newest stays on top), versions unique, and both bodies non-empty — pinned by `src/changelog/entries.test.ts`.
- Keep phrases that tests assert on in plain text runs: markdown formatting splits text nodes, and testing-library's `getByText` matches direct text nodes only.

Rendering & UI wiring:

- `pages/Changelog.tsx` (`/changelog`, authenticated, lazy) renders the entries as a Mantine `Timeline` with `MarkdownView` bodies in the viewer's language, and calls `markChangelogSeen()` on mount. **Bodies are authored EN+PL only, by policy** — a new shipped UI language does NOT add changelog fields; non-authored languages read the English body (`AUTHORED_LANGUAGES` in the page). `components/MarkdownView.tsx` (Typography + react-markdown + remark-gfm/gemoji, all lazy-chunk-only deps) is the one markdown renderer — reuse it for future markdown content.
- `components/VersionStamp.tsx` shows `v<APP_VERSION> · <sha> · <time>`; its optional `to` prop renders it as a router link — the navbar instance links to `/changelog`, the Login/AuthCard instance deliberately stays plain (the route is behind auth). A "Changelog" nav item (`CHANGELOG_NAV` in `App.tsx`) is pinned last, directly above the stamp.
- The **"what's new" dot** is a red Mantine `Indicator` around the navbar stamp in `App.tsx`, shown while localStorage `toadie.changelog` (`{seenVersion}`) differs from `APP_VERSION`. It's driven by `hooks/useChangelogSeen.ts` via `useSyncExternalStore` over a module-level listener set — do **not** replace that with a plain localStorage read in state: the shell renders before the page's mark-seen effect, so the dot would only clear on the next navigation. The seen-state is device-level (survives logout, like `toadie.lang`) and hand-rolls its guarded read/write, not `useStoredState` (that hook owns the `toadie.viewSettings.*` namespace).
- Tests: `pages/Changelog.test.tsx`, `changelog/entries.test.ts`, the dot/nav cases in `App.test.tsx`, the link/prefix cases in `components/VersionStamp.test.tsx`, and the e2e `changelog.spec.ts` (device-local state only — owns nothing server-side).
