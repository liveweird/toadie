# Running, packaging, and deploying the toadie stack

## Packaging

Package the server for deployment with `./gradlew :server:installDist` (output under `server/build/install/server/`, launcher `bin/server`). **Do not use `:server:buildFatJar`** — the shadow plugin collapses the duplicate `META-INF/services/org.flywaydb.core.extensibility.Plugin` descriptors and the fat JAR NPEs at startup inside Flyway's plugin registry. `installDist` keeps each dependency JAR separate, so Flyway's `ServiceLoader` discovery works exactly as under `:server:run`.

## JVM footprint tuning

JVM footprint tuning is baked into the `application {}` block in `server/build.gradle.kts` via `applicationDefaultJvmArgs` = `-XX:+UseSerialGC -Xmx256m -XX:TieredStopAtLevel=1`, so it flows into both `bin/server` (→ Docker image) and `:server:run` (the Gradle `test` task is unaffected). Measured (in Lettuce, the same stack) on a 512 MiB Linux container: baseline G1 drifts **~345→410 MiB RSS** as it grows its heap, vs a steady, deterministic **~270 MiB** with these flags (**~25% lower and predictable**); startup is ~1.6 s either way, so the win is memory, not startup. SerialGC removes G1's per-heap overhead (~75 MiB); `-Xmx256m` caps a heap that holds no large caches (drop to `192m` to trim ~25 MiB more); C1-only (`TieredStopAtLevel=1`) trims code-cache + C2-compiler memory (~50 MiB) at the cost of peak CPU-bound throughput (irrelevant here — **remove that flag if the service ever runs hot**). Override per-deploy with `JAVA_OPTS`/`SERVER_OPTS` (the launcher appends both). Container ceilings match: `mem_limit: 512m` in `docker-compose.yaml`, `resources.limits.memory: 512Mi` (request `320Mi`) in `k8s/app-deployment.yaml`. This was evaluated (in Lettuce) instead of a GraalVM native-image migration, which the reflection/ServiceLoader-heavy stack (Ktor config modules, Flyway, Exposed, OTel, Logback, java-jwt) makes costly for little benefit on a long-running internal service.

## Running the full stack

Two ways to run, sharing the same `docker-compose.yaml`. All ports deliberately avoid Lettuce's (8080/5432/5173), so both stacks can run side by side on one machine:

- **One command (clone & run / demo):** `docker compose up --build` builds the SPA, builds the server, starts PostgreSQL, runs Flyway on boot, and serves everything at `http://localhost:8081` (Swagger at `/openapi`; sign in as `admin@toadie.local` / `changeme`). Tear down with `docker compose down` (add `-v` to drop the DB volume).
- **Local development (hot reload):** `docker compose up postgres` (host port **5433** → in-container 5432) + `./gradlew :server:run` + `cd web && npm run dev` (Vite on `:5174`, proxying `/api` → `:8081`).
- **Local Kubernetes (OrbStack):** the deployment is written for a TLS-terminating **ingress-nginx** front door at a real hostname (`k8s/templates/app-ingress.yaml`). ⚠ **Community ingress-nginx was RETIRED in March 2026** (https://kubernetes.io/blog/2026/01/29/ingress-nginx-statement/) — no further security patches; this manifest is the LOCAL-PROOF reference only, and any real production deployment MUST migrate to a maintained controller or the Gateway API (a behavior migration — re-verify the proxy contract: `HTTP_PROXY_HOPS`, the narrowed `XForwardedHeaders` list, the 308/HSTS/XFF-replacement assumptions, and `ProductionHttpTest`). Order: (1) `docker build -t toadie-app:latest .`; (2) install the controller once — `kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.15.1/deploy/static/provider/cloud/deploy.yaml` then `kubectl wait -n ingress-nginx --for=condition=ready pod -l app.kubernetes.io/component=controller --timeout=180s` (its admission webhook rejects Ingresses until the pod is Ready; a Lettuce deployment on the same cluster already has it — it is shared); read its LoadBalancer EXTERNAL-IP (`kubectl get svc -n ingress-nginx ingress-nginx-controller` — OrbStack hands every LB the node IP) and pick the host `toadie.<that-ip>.nip.io` (resolves without touching /etc/hosts); (3) `kubectl create namespace toadie`, then create the out-of-band config BEFORE applying — the Secret `toadie-secrets` (command in `k8s/templates/secret.yaml`), the TLS cert `toadie-tls` (self-signed recipe with the host as SAN in `k8s/templates/tls-secret.yaml`; cert-manager in real deployments), and the ConfigMap that carries the public URL: `kubectl -n toadie create configmap toadie-config --from-literal=MAIL_APP_URL=https://$HOST`; (4) apply the host-agnostic workloads with `kubectl apply -f k8s/` (deployment/service/postgres/PVC — **non-recursive on purpose so `k8s/templates/` is skipped**: `kubectl apply` over an existing Secret REPLACES its values, so re-applying the placeholder template would swap the real `JWT_SECRET` for the burned one and fail the app closed on its next restart — the 2026-09-05 audit reproduced exactly that with the old flat layout, plus a postgres volume initialised with the placeholder password), then the Ingress from its template: `sed "s#toadie.example.com#$HOST#g" k8s/templates/app-ingress.yaml | kubectl apply -f -`. **The Ingress lives in `k8s/templates/` on purpose** so the directory apply can never revert its substituted host, and the deployment carries NO baked hostname (`MAIL_APP_URL` comes from the `toadie-config` ConfigMap) — so `kubectl apply -f k8s/` is safe to re-run. The three per-deployment values that must agree: the Ingress host (twice), the `toadie-config` `MAIL_APP_URL`, and the cert SAN. Then browse `https://$HOST/` (self-signed → accept the warning; curl `-k`). The `k8s/` manifests are kompose-derived from `docker-compose.yaml` with these fixes baked in: the app image is the locally built `toadie-app:latest` with `imagePullPolicy: IfNotPresent` (OrbStack's cluster shares the Docker image store — no push needed), the postgres healthcheck is a proper argv-list exec probe doubling as the readiness gate, the app Service is `ClusterIP` behind the Ingress (was `LoadBalancer` until v1.22.0 — switching a LIVE Service can be rejected because of the allocated nodePort: `kubectl -n toadie delete svc app` first, then apply; `kubectl -n toadie port-forward svc/app 8081:8081` for pod-direct debugging), and the app exposes dedicated health endpoints (`plugins/Health.kt`): **`/healthz`** (liveness — process-alive only, never hits the DB, so a DB outage does not restart-storm the pod) and **`/readyz`** (readiness — a cheap DB round-trip over the namespaces dictionary, single-flight and bounded to 2 s (`READYZ_TIMEOUT_MS`), so an unreachable DB answers a 503 under the probe's `timeoutSeconds: 3` instead of hanging the probe until the OS gives up on the connect — Toadie's addition over Lettuce's copy, measured 2–7 s unbounded). A **`startupProbe` on `/healthz`** gives JVM boot + Flyway up to ~150s before the liveness clock starts. **Every probe sends `X-Forwarded-Proto: https`** — the header the ingress sets; without it production mode answers the plain-HTTP probe with a 301 to `https://<pod-ip>/` that the kubelet FOLLOWS (same host) into a refused `:443`, so probes never pass and the pod crash-loops (the audit's second reproduced blocker — the old probes hit `/` bare). After rebuilding the image, `kubectl -n toadie rollout restart deployment/app` picks it up. **What the ingress does for you (ingress-nginx defaults):** plain `http://$HOST/` answers a 308 to https at the edge (the app's own 301 fires pod-direct only), `X-Forwarded-For` is REPLACED with the real client IP (raise `HTTP_PROXY_HOPS` only for an APPENDING chain — see `application.yaml` `http.proxyHops`), and `Strict-Transport-Security` is overwritten by the controller (HSTS policy = its configmap). **Pod-direct access in production mode** (port-forward) gets the app's 301 to `https://<host>/` — for API checks send `-H 'X-Forwarded-Proto: https'` (trusted because of `HTTP_BEHIND_PROXY=true`). **Running the e2e suite against the cluster** needs a DEVELOPMENT-mode app with the pristine seed admin (a production boot rotates it whenever `ADMIN_INITIAL_PASSWORD` is set): `kubectl -n toadie set env deployment/app KTOR_DEVELOPMENT=true ADMIN_INITIAL_PASSWORD-` on a fresh database, keep `docker compose` DOWN (the suite reuses a stack it finds on :8081), then `cd e2e && E2E_BASE_URL=https://$HOST E2E_INSECURE_TLS=1 npm test` (the mail specs need Mailpit and skip without it). Back to production: re-apply the deployment from the manifest (restores the `ADMIN_INITIAL_PASSWORD` secretKeyRef) and `kubectl -n toadie rollout status deployment/app`. **Teardown:** `kubectl delete -f k8s/` removes the workloads *including the DB volume* (the `local-path` storageclass reclaim policy is Delete) — the Secrets, ConfigMap, Ingress and the controller stay (`kubectl -n toadie delete ingress app secret toadie-secrets toadie-tls configmap toadie-config`; leave the controller if Lettuce uses it); to stop the workloads but keep the data, `kubectl -n toadie scale deployment app postgres --replicas=0` instead. **Credentials — provisioning vs rotation:** the database password lives INSIDE postgres once the volume is initialised; a later mismatch between the Secret and the database is fixed by rotating in both places (`ALTER ROLE toadie PASSWORD` + a new Secret + an app restart), never by deleting the volume, which is the workspace. **Secrets:** the deployments consume the `toadie-secrets` Secret via `secretKeyRef` (`JWT_SECRET`, `POSTGRES_USER`/`POSTGRES_PASSWORD`, `ADMIN_INITIAL_PASSWORD`, optional `SMTP_USER`/`SMTP_PASSWORD`); never apply the templates (the JWT placeholder is on the burned list in `plugins/Security.kt`). The app deployment runs production mode (`KTOR_DEVELOPMENT=false`, `HTTP_BEHIND_PROXY=true`, `HTTP_PROXY_HOPS=1`, `MAIL_APP_URL` from the ConfigMap); for throwaway plain-HTTP browser testing without the ingress, flip `KTOR_DEVELOPMENT` to `"true"` in `k8s/app-deployment.yaml` (HTTPS redirect/HSTS off, seed credentials tolerated, exactly like the compose demo) and port-forward the ClusterIP service.

The root `Dockerfile` is a 3-stage build: (1) `node` builds `web/dist` (`npm ci --legacy-peer-deps`), (2) `eclipse-temurin:21-jdk` runs `:server:installDist` (the committed `gradle.lockfile`s are copied in beside the build scripts — dependency locking is on, so a missing lockfile fails the image build), (3) `eclipse-temurin:21-jre` runtime (one JDK line across the build stage, `mise.toml` and `jvmToolchain(21)`) bundles the install image **and** the built SPA, sets `WEB_STATIC_DIR=/app/web` and `KTOR_DEVELOPMENT=false`, and runs `bin/server`. The `app` Compose service points the `POSTGRES_*` env vars at the `postgres` service host (`postgres:5432` in-network) and waits on its healthcheck. `.dockerignore` keeps build outputs / `node_modules` out of the build context; `.git` is **included** on purpose — the SPA build stage reads the commit sha/timestamp from it for the version stamp (see "Build version stamp" in `web/CLAUDE.md`). Note the volume mount: postgres 18+ images keep data in a versioned subdir of `/var/lib/postgresql`, so the compose volume mounts that path (the pre-18 `/var/lib/postgresql/data` path makes the container unhealthy).

## Reproducibility — what is pinned, and what deliberately is not

Pinned: direct dependency versions (`gradle/libs.versions.toml`, `web/package.json` + `package-lock.json` installed with `npm ci`), the transitive Gradle graph (dependency locking, `gradle.lockfile` in `core/` and `server/` + the root `settings-gradle.lockfile` and `buildscript-gradle.lockfile` — `./gradlew build --write-locks` after a dependency change, commit the result), the Gradle distribution checksum (`distributionSha256Sum` in `gradle-wrapper.properties`), the toolchains (`mise.toml`: Temurin 21 + Node 24, matching the Dockerfile and the e2e workflow), and base images by minor tag (`node:24-alpine`, `eclipse-temurin:21-jdk/-jre`, `postgres:18-alpine`, `axllent/mailpit:v1.30`).

Deliberately NOT adopted (the 2026-09-05 deployment audit raised them; decided against, don't re-raise without a new reason): Gradle **dependency verification metadata** (per-artifact checksums — a maintenance sink for a repo with no dependency-bump bot), **base images by digest** and a **registry-published release image by digest** (a digest pin without automation freezes security patches; the documented target is OrbStack's shared image store), a **versioned `apk add git`**, and a **`.git`-less build context** (`COPY .git .git` feeds the version stamp; `web/vite.config.ts` already honours `GIT_SHA`/`GIT_COMMIT_TIME` from the environment, so an `ARG` pass-through is the one missing piece — add it only when a source-archive build actually appears).
