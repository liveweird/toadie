### Authorization model

Layered RBAC. Implemented in the `server/src/main/kotlin/authz/` package.

- **Global roles are an additive set**: every user is implicitly a regular user (USER is the baseline — never transmitted), and additional roles — currently only `ADMIN` (`UserRole` in `users/User.kt`; a future role is just a new enum value) — only ever ADD privileges. The API carries them as a `roles` array (`[]` = regular user); `isAdmin()` (`authz/Guards.kt`) = `ADMIN ∈ roles`. Storage is a single `users.role` column with a CHECK (V1) — the **wire shape is already the set** (`roles` claim + `LoginResponse.roles`), so moving to a Lettuce-style `user_roles` join table when a second additional role arrives never breaks issued tokens or clients. **ADMIN is the management role**: it owns the whole user-management surface (the `/users` CRUD below) and may reset any user's password (`requireSelfOrAdmin`'s admin branch); future management surfaces (teams…) attach to it, and — the Lettuce rule worth keeping — ADMIN gets **no special access to other users' content** (the catalog workspace already applies it); there an admin is an ordinary user.
- **Login** issues a **pair** of JWTs, both carrying `email`, `userId`, a `roles` array claim, and a `typ` claim (`"access"` / `"refresh"`), minted by `auth/Tokens.kt` (`JwtConfig.issueAccessToken` / `issueRefreshToken`). The short-lived **access** token (`jwt.accessExpiresInSeconds`, default 900) is the API bearer; the longer-lived **refresh** token (`jwt.refreshExpiresInSeconds`, default 3600) is exchanged at `POST /api/v1/refresh` for a fresh pair. `LoginResponse` (also the `/refresh` response) exposes `token`/`expiresAt`, `refreshToken`/`refreshExpiresAt`, `userId`, and `roles`. The `jwt {}` verifier in `plugins/Security.kt` additionally requires `typ == "access"` and a non-revoked `jti`, so a refresh token cannot authenticate an API call.
- **Session auto-extension (pure sliding).** `/api/v1/refresh` (rate-limited, no `authenticate` — the access token may be expired) verifies the refresh token's signature/issuer/audience/`typ`/non-revocation, then does **one** `userService.read(userId)` to confirm the user is still active (soft-delete-filtered) and pick up their current roles/email, **rejects tokens whose `iat` predates `users.password_changed_at`** (compared at second granularity — JWT `iat` is second-precision; a missing `iat` counts as epoch 0), and mints a fresh pair. Superseded tokens are **not** rotated out — they stay valid until their own expiry (no blocklist write on refresh); only an idle session (no refresh within the refresh TTL) ends. Every rejection is audited (`refresh.rejected` with `reason`). `/api/v1/logout` revokes the access `jti` (from the principal) **and**, if the client sends the refresh token in the body (`LogoutRequest`), that token's `jti` too — into the `revoked_tokens` table (`auth/TokenBlocklistService.kt`; the revoke path prunes expired rows). Frontend: `web/src/api/http.ts` `authedFetch` silently refreshes (single-flighted via a module-level in-flight promise) and retries once on a `401`; on a definitive refresh rejection it clears the session and signs out.
- **Guards** in `authz/Guards.kt` are plain `suspend`-friendly function calls used at the top of each route handler — there is no Ktor plugin or DSL. Each route reads `call.caller()` (which parses the JWT claims into a `CallerPrincipal{userId, email, roles}` — missing/unknown claims throw `UnauthorizedException`) and then invokes the relevant guard: `requireAdmin(caller)` and `requireSelfOrAdmin(caller, targetUserId)` today; new guards join this file so the whole policy stays in one place.
- **Resource rules**:
  - `/api/v1/files` (all five operations, plus `GET …/errors`, `POST …/check`, `GET …/graph`, `GET …/export`, `POST …/import`, `POST …/import/check`, and the SSRF-guarded `POST …/fetch` — see "Outbound URL fetch" in `.claude/docs/security.md`) → **any authenticated user** — the catalog is a shared workspace: every user may create, edit, and delete every file (creator recorded as `created_by` for display and audit), and ADMIN gets **no special content access** here (the standing Lettuce rule, applied from the first content feature). The only guard is the bare `call.caller()`; existence disclosure is a plain 404 (nothing to hide behind a 403). The list, graph, and errors GETs declare ONE shared filter set — name/namespace/kind/tag/type/lifecycle/owner/label+labelValue (`catalog/CatalogFileFilter.kt`: the SQL predicate for the list, the SAME semantics in memory for the graph and the Errors report; `kind` and `labelValue` are the repeated any-of/IN params — labelValue requires `label` — and owner matches by REFERENCE RESOLUTION: every stored spelling that resolves to the picked entity); graph/errors filters narrow which files are EXPANDED/REPORTED while targets keep resolving against the whole workspace. Every WRITE additionally resolves its namespace against the `namespaces` dictionary (`CatalogFileService.resolvedNamespace`, HARD — no grandfathering, never waivable): blank/omitted → the ADMIN-flagged DEFAULT entry (none flagged → `400`), a concrete value must be an active entry → else `400`; and computes its SOFT findings (`CatalogFileService.softFindings` — the registry checks via the pure `registryFindings` in Errors.kt over a `loadRegistrySnapshot()` taken in the write's transaction, plus reference resolution via `checkDocument`): every `metadata.labels` key must be a registered active label allowed for the file's kind with the value from its closed list, every `metadata.annotations` KEY registered and kind-allowed (values stay free), every `metadata.tags` entry in an active category whose kinds include the file's kind, a non-blank `spec.type` in the kind's active type dictionary (a kind with no dictionary allows none), a non-blank `spec.lifecycle` an active GLOBAL lifecycles entry, and every entity reference resolving to a stored active entity of a kind the field allows AND never the entity itself (`SELF_REFERENCE` — checked against the payload's own identity, so it holds uniformly for create/update/rename/import). **Strict by default**: any soft finding → ONE aggregated `400` (no grandfathering). **`allowInvalid=true`** (query param on create/replace) WAIVES the soft findings and stores anyway — the editor's Save-anyway modal sends it after a confirmed strict rejection, the audit event carries `waivedFindings`, and the Errors report tracks the stored findings (deleting a referenced entity stays ALLOWED — referrers go dangling and block their next STRICT save; import resolves against the workspace PLUS the whole batch, order-independent). Import ALWAYS waives: soft-flawed documents store as `CREATED_WITH_FINDINGS` rows (message = the findings), and only structural validation and namespace resolution still skip a document as `INVALID`. The three check endpoints and export are pure reads/computations — no audit events; `POST …/check` returns the same soft findings a strict save would reject (references + registry checks), so findings mean "a strict save would be refused", and `POST …/import/check` is the import's DRY-RUN: the identical per-row classification (structural validation, namespace resolution, identity conflicts against the workspace AND within the batch, soft findings) with nothing stored — `fileId` stays null and the statuses read as predictions (a snapshot: a concurrent write may change the real outcome). Import creates files with the ordinary machinery, so each stored document emits the ordinary `catalog_file.created` audit (plus an `import` marker, and `withFindings` on waived rows); rejected documents become result rows (report & skip), never errors. `GET …/errors` additionally runs two REPORT-ONLY checks over stored content — `STRUCTURE_INVALID` (the structural validation no longer accepts the row; the finding carries the validator's message) and `NAMESPACE_NOT_ALLOWED` (the stored namespace left the dictionary) — verdicts on rules that stay HARD on every write, so they never join the soft findings or `POST …/check`.
  - `/api/v1/users` (list/create) and `PUT`/`DELETE /api/v1/users/{id}` → **ADMIN only** — the whole management surface is admin-gated (the list included; regular users keep only the self password change). `GET /users/{id}` → target user or ADMIN, **guard-before-read** (an unauthorized caller 403s uniformly whether or not the id exists). Two protections with a deliberate 403/409 split: **self-delete is a `ForbiddenException` (403)** — a permissions-shaped rule about WHO acts — while **deleting or demoting the LAST active administrator is a `ConflictException` (409)** — a state-shaped rule about what the system can afford to lose. Initial passwords are client-generated (the SPA) and stored only as bcrypt hashes; no response carries plaintext.
  - `/api/v1/dictionaries/{dictionary}` (two slugs: `namespaces` and `lifecycles`) → `GET` **any authenticated user** (the read-only lists back the SPA's Namespaces/Lifecycles pages and the catalog form's namespace/lifecycle Selects); `PUT` **ADMIN only**, with `requireAdmin` BEFORE slug resolution (a non-admin probe gets a uniform 403 whether or not the slug exists — the guard-before-read idiom). The PUT is a whole-document replace (payload order = stored order, omitted entries soft-deleted). The default flag branches per dictionary (`Dictionary.usesDefault`): a non-empty `namespaces` document must flag EXACTLY one entry `isDefault` — what blank catalog-file namespaces resolve to — while `lifecycles` has no default and rejects any flagged item with `400`. Audits `dictionary.updated` with the added/renamed/removed counts plus the flagged default value (null for lifecycles).
  - `/api/v1/labels` → `GET` **any authenticated user** (the registry backs the SPA's Labels page and the catalog editor's label pickers, unpaged); `POST` + `PUT`/`DELETE /api/v1/labels/{id}` **ADMIN only**, with `requireAdmin` BEFORE the id lookup (guard-before-read: a non-admin probe gets a uniform 403 whether or not the id exists). Per-entity CRUD (not the dictionary's whole-document replace — a label is key + closed value list + applicable kinds); a case-insensitive key clash with an active label is `409`; deleting/renaming a label makes files carrying the old key strict-invalid on their next save (deliberate). Mutations audit `label.created`/`label.updated`/`label.deleted`.
  - `/api/v1/annotation-keys` → `GET` **any authenticated user** (the registry backs the SPA's Annotations page and the catalog editor's annotation key Select, unpaged); `POST` + `PUT`/`DELETE /api/v1/annotation-keys/{id}` **ADMIN only**, with `requireAdmin` BEFORE the id lookup (guard-before-read). The labels shape minus the value dimension (a row = key + applicable kinds; annotation VALUES stay free strings); a case-insensitive key clash with an active row is `409`, and the server-written `backstage.io/*` keys cannot be registered (`400`); deleting/renaming a key makes files carrying it strict-invalid on their next save (deliberate). Mutations audit `annotation_key.created`/`annotation_key.updated`/`annotation_key.deleted`.
  - `/api/v1/tag-categories` → `GET` **any authenticated user** (the registry backs the SPA's Tags page and the catalog editor's grouped tags picker, unpaged); `POST` + `PUT`/`DELETE /api/v1/tag-categories/{id}` **ADMIN only**, with `requireAdmin` BEFORE the id lookup (guard-before-read). Per-entity CRUD like labels (a category = internal name + tag list + applicable kinds); a case-insensitive name clash with an active category is `409`, and so is a tag already belonging to ANOTHER active category (the one-category-per-tag invariant, service-enforced — moving a tag is remove-then-add in two saves); deleting/editing a category makes files carrying removed tags strict-invalid on their next save (deliberate). Mutations audit `tag_category.created`/`tag_category.updated`/`tag_category.deleted`.
  - `/api/v1/entity-types` → `GET` **any authenticated user** (the per-kind type dictionaries back the SPA's Types page and the catalog editor's Type Select, unpaged — at most six rows); `POST` + `PUT`/`DELETE /api/v1/entity-types/{id}` **ADMIN only**, with `requireAdmin` BEFORE the id lookup (guard-before-read). Per-entity CRUD like labels/tags, but the row IS a kind (one dictionary per type-bearing kind — User excluded; a kind already holding an active dictionary is `409`), and the dictionaries are INDEPENDENT (the same value may be allowed for several kinds — no cross-row check). Deleting/narrowing a dictionary makes files carrying removed types strict-invalid on their next save (deliberate; a kind with NO dictionary allows no types at all). Mutations audit `entity_types.created`/`entity_types.updated`/`entity_types.deleted`.
  - `/api/v1/lenses` → ALL routes **any authenticated user** — lenses are per-user CONTENT (no admin gate anywhere; ADMIN gets no special access, the standing rule): a lens = a named snapshot of the shared catalog filter set (the nine slots) with `visibility` PRIVATE or PUBLIC. `GET` lists the caller's OWN lenses (both visibilities) plus everyone's PUBLIC ones, unpaged; `POST` creates with the caller as creator (name unique per owner among active lenses, case-insensitively → `409`; the payload is validated STRUCTURALLY only — lengths, kind whitelist, labelValue-requires-label — never against the registries, a lens holding a since-removed value simply matches nothing); `PUT`/`DELETE {id}` are **creator-only** (overwrite, rename, and the visibility flip are all the one whole-lens PUT). **Existence disclosure — a deliberate HYBRID of the two idioms**: a foreign PRIVATE (or unknown/soft-deleted) id → uniform **404** on any mutation (a private lens's existence is itself the secret; `LensService.mutationVerdict`, decided in the mutation's transaction), while a foreign PUBLIC lens — in everyone's list anyway — → the honest **403** (audited `authz.denied` via the thrown `ForbiddenException`). The verdict runs BEFORE payload validation, so 403/404 win over 400 (the password-PUT precedent — the PUT route deliberately skips route-side `validateLensRequest`). Mutations audit `lens.created`/`lens.updated`/`lens.deleted`. Tests: `LensTest`.
  - `PUT /api/v1/users/{id}/features` → ADMIN only; **self allowed** (an admin adjusting their own flags is a feature, and the users routes are never gated, so a fully self-disabled admin can always get back); unknown/soft-deleted target → 404; unknown feature name → 400 (enum decode); wholesale replace (idempotent — same-set re-PUT is 204, not 409); audited `user.features_changed` (featuresFrom/featuresTo) only on an actual change. **Per-user feature flags (V12, Lettuce's model)**: `Feature { MFA }` stored as the DISABLED set (`user_disabled_features`, no row = enabled). **`MFA` is inverted-default and login-scoped** — every user starts with the MFA row present (the V13 seed + the `UserService.create` chokepoint), so email MFA is opt-in; it gates the LOGIN FLOW only, and no route names it in `requireFeatureEnabled` (which awaits Toadie's first area-gating feature; run it as the FIRST guard when one arrives — before any read, so a disabled caller gets a uniform 403 even for a missing id). Mind the wholesale-replace PUT: a disabled set omitting MFA — including the empty "re-enable everything" array — ENABLES the second factor. The set rides both JWTs as the `disabledFeatures` claim (missing claim = empty — outstanding tokens survive the deploy; unknown value = 401) and `LoginResponse`/`UserResponse.disabledFeatures`, so a change takes effect at the target's next refresh (≤15 min) or login. Users list: `feature=<F>&featureEnabled=true|false` filter pair (must come together, 400 otherwise). SPA: `hasFeature()` (`api/session.ts`, localStorage `toadie.auth.disabledFeatures`), the per-user editor `/users/:id/features` (the Users table's Features button) and the admin per-feature screen `/feature-flags` (state filter + bulk enable/disable over every row matching the current filters, behind a count-stating confirm — a client-side loop of the same per-user wholesale PUTs). Tests: `FeatureFlagsTest` + the GuardsTest/AuditTest cases.
  - `PUT /api/v1/users/{id}/language` → **target user or ADMIN** (`requireSelfOrAdmin`, V18 — Lettuce's v2.21.0 model): the ONE synced per-user language, set at create (`UserCreateRequest.language`, default `"en"`), applied to the SPA at sign-in (rides `LoginResponse`, applied by `persistSession` on login/MFA/refresh) and used for every email sent to the user (read fresh at send time). The header language switcher is the self-service writer (fire-and-forget save on switch); the whole-user PUT deliberately never touches it. Unsupported code → 400 (after the guard — 403 wins); idempotent; audited `user.language_changed` on an actual change. Tests: `UserLanguageTest`.
  - `GET`/`PUT /api/v1/users/{id}/graph-layout` → **target user or ADMIN** (`requireSelfOrAdmin`, guard-before-read — a forbidden caller 403s uniformly whether or not the id exists): the per-user Graph-page layout document (V19) — `{mode: auto|manual, positions}` with positions keyed by node id. The PUT is a **wholesale replace** (the SPA merges over its GET copy — never send only the visible nodes' positions); GET returns the default document (`auto`, empty) for a live target that never saved. Validation after the guard (mode whitelist, ≤1000 positions, key length/control-char rules → 400); unknown/soft-deleted target → 404. **Deliberately UNAUDITED** — the one sanctioned audit exception: pure view state written on every drag stop (an event per drag would be spam); denials still emit `authz.denied`. Tests: `GraphLayoutTest`.
  - `PUT /api/v1/users/{id}/password` → target user or ADMIN (`requireSelfOrAdmin`). New password must be ≥ 10 chars (`MIN_PASSWORD_LENGTH` in `users/UserRoutes.kt`) and ≤ 71 UTF-8 bytes (`MAX_PASSWORD_BYTES`, `auth/Passwords.kt` — the bcrypt ceiling), else `400`. A **self-change** (even by an admin) additionally requires a correct `currentPassword` in the body (else `403`, audited `password.change_denied`) — checked BEFORE the length validation, so 403 wins over 400 (the convention everywhere); an admin resetting **another** user's password does not. A successful change stamps `users.password_changed_at`, which invalidates all outstanding refresh tokens (see "Session auto-extension"); already-issued access tokens keep working until their ≤15-min expiry (documented bounded window). Covered by `PasswordChangeTest`.
- **Existence disclosure (403 vs 404) — deliberate policy (API-ERR-006)**: two sanctioned idioms, and every new resource picks one consciously rather than mixing them. **Guard-before-read** (Lettuce's `GET /users/{id}`): a forbidden caller gets a uniform 403 whether or not the id exists — use it where existence itself is sensitive. **Read-before-guard** (Lettuce's feedback/notification GETs): missing → 404, existing-but-forbidden → 403 — acceptable where ids are sequential and existence is no secret. The password PUT effectively guards first (`requireSelfOrAdmin` needs no read), then maps a zero-row update to 404 — safe because the only callers past the guard are the target and admins.
- **Audit on denial**: every 403 emits `authz.denied` (method/path/byUserId/detail) from the `ForbiddenException` handler in `plugins/ErrorHandling.kt` — denials are part of the security trail, and route code gets it for free by **throwing**, never hand-rolling a 403 response. See "Audit trail" in `.claude/docs/observability.md`.
- **Exceptions**: `UnauthorizedException` (→ 401), `ForbiddenException` (→ 403), `NotFoundException` (→ 404), `ConflictException` (→ 409), and `TooManyRequestsException` (→ 429) live in `authz/Exceptions.kt` and are mapped in `plugins/ErrorHandling.kt`. **All error bodies are RFC 7807 `application/problem+json` (API-ERR-001/002)** (`ProblemDetail{type,title,status,detail,instance}`) — emit them via the `ApplicationCall.respondProblem(status, detail)` helper (it uses an explicit `TextContent` so ContentNegotiation does not relabel the media type as `application/json`). `StatusPages` routes `BadRequestException`→400 (**with fixed vocabulary for converter failures**: a `ContentConvertException` anywhere in the cause chain — ContentNegotiation's malformed-JSON wrap, whose raw message carries the target FQCN — answers "Request body is invalid or does not match the expected schema", and the Resources decode wrap "Can't transform call to resource" answers "Path or query parameter is malformed"; our validators' own messages, cause-less, pass through), `CannotTransformContentToTypeException`→400 (a body-less/Content-Type-less POST never enters ContentNegotiation, so it isn't wrapped in BadRequestException and would otherwise escape to the 500 catch-all; deliberately NOT the abstract ContentTransformationException parent, which would mislabel a future 413/415), the typed exceptions as above (**the route 404 convention**: read preambles and zero-row mutation results `throw NotFoundException("<Resource> not found")` — never a hand-rolled `respondProblem(NotFound, …)` + return), unique-violation `23505`→409 and NUL-byte `22021`→400 (via the R2DBC/Exposed cause-chain walkers), and a catch-all `Throwable`→500 (logged) through that helper. A `status(TooManyRequests)` handler additionally gives the per-IP `RateLimit` plugin's bodiless 429 a generic problem body — **that handler rewrites any non-StatusPages 429**, which is why caller-specific 429s (the login lockout) must go through `TooManyRequestsException` (handled calls are marked and skipped) — and a sibling `status(MethodNotAllowed)` handler gives routing's bodiless wrong-method 405 a problem body too (no `Allow` header — Ktor doesn't surface the allowed-method set; test with the default client, the conformance plugin would rightly flag the out-of-spec operation). A pre-routing intercept in `configureErrorHandling` additionally 400s any `/api/` path with a negative-integer segment (kotlinx decodes `UInt` via `toInt().toUInt()`, so `/users/-1` would WRAP to 4294967295 and flow into the normal lookup instead of failing as the spec's `minimum: 0` promises). The JWT `challenge` in `plugins/Security.kt` also calls `respondProblem` (it runs outside `StatusPages`). Test HTTP clients must register the `application/problem+json` content type (`json(contentType = ContentType.parse("application/problem+json"))`) to decode error bodies with `body<ProblemDetail>()` — `toadieTestClientDefaults()` does.
- **Tests**: `GuardsTest` covers the guard matrix, `AnonymousAccessTest` + the feature verb sweeps the 401 surface, `UserRoutesTest` the management CRUD + protections (with `TestUsers.withSoloAdmins` isolating the last-admin 409s in the shared container), `PasswordChangeTest` the self-vs-admin rules, `AuditTest` the denial and mutation events. The shared `TestUsers.seed` helper defaults to `role = UserRole.ADMIN` so privileged fixtures are terse; pass `role = UserRole.USER` when you need a non-privileged caller.
